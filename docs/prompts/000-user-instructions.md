# Глобальные предпочтения пользователя

## Дизайн интерфейсов во всех проектах

- Никакого шаблонного «ИИшного» дизайна. Перед проектированием нового UI изучать живые, опубликованные аналоги и их конкретные решения; фиксировать ссылки на референсы в проекте.
- Никогда не использовать декоративную нумерацию секций и блоков вроде «01», «02», «03», «04». Числа допустимы только как необходимые данные: даты, время, возраст, количество, реальные шаги процесса.
- Избегать узнаваемого «AI slop»: повторяющихся композиций, случайных звёздочек и фигур, бессмысленных бейджей, одинаковых карточек и искусственных слоганов. Каждый элемент должен иметь конкретную функцию или обоснование в выбранном дизайне; наличие референсов само по себе не оправдывает шаблонный результат.
- Выбирать типографику, палитру, оттенки, иконки, плотность и композицию осмысленно под конкретный продукт. Не повторять автоматически стандартные сочетания шрифтов, цветов, скруглённых карточек и иконок из предыдущих проектов.
- При значительной переработке UI сначала анализировать цветовые роли и пропорции, шрифты и иконографику конкретных опубликованных аналогов, затем показывать несколько самостоятельных визуальных вариантов до реализации. Не ограничиваться одним макетом с заменой цветовых переменных.
- Сохранённые наблюдения и референсы находятся в `C:/Users/Rinni/.codex/design-reference-library.md`. Использовать их как библиотеку исследований, а не как новую универсальную палитру или обязательный набор шрифтов. Для языков продукта проверять глифы фактических файлов шрифтов; для кыргызского — в том числе Ңң, Өө, Үү.
- Не использовать неизменённый внешний вид компонентов UI-библиотеки как готовый дизайн. Библиотечные примитивы можно применять для поведения и доступности, но внешний вид требуется адаптировать.
- Не добавлять декоративные слоганы, искусственные описания, ненужные бейджи, пояснения очевидных действий и другие лишние тексты. Оставлять названия, действия, необходимые данные и сообщения об ошибках. Не убирать подписи и доступные названия, которые нужны пользователю.
- Не использовать дефолтные календари и браузерные date/time поля в качестве финального интерфейса. Создавать или существенно адаптировать визуальные компоненты выбора даты и времени; сохранять клавиатурное управление, ввод с точностью до минуты и доступность.
- Проверять фактический внешний вид в браузере на большом и маленьком экране до завершения. Смена пары CSS-переменных не считается полноценной переработкой дизайна, когда пользователь просит переделать весь UI.

## Организация стилей во всех проектах

- Всегда использовать SCSS/Sass для авторских стилей. Писать их в `.scss`/`.sass`, а не в чистом CSS. В новых проектах сразу настраивать компиляцию Sass.
- Не складывать всю стилизацию приложения в один файл. Разделять стили по компонентам и функциональным областям; общие токены, миксины и базовые стили держать в отдельных модулях. Общая точка входа должна преимущественно подключать модули.
- В Vue компонентные стили оформлять через `<style lang="scss" scoped>` либо отдельный SCSS-модуль компонента. Глобальные стили подключать явно и ограничивать необходимыми общими правилами.
- Использовать современную модульную систему Sass (`@use`/`@forward`), осмысленные переменные и умеренную вложенность. Не допускать длинных цепочек селекторов и бесконтрольного применения `!important`.

## Авторство Git во всех проектах

- Коммиты и push выполнять только через аккаунт пользователя. Перед первым коммитом проверять его настроенные Git-имя и email; author и committer должны соответствовать этой идентичности.
- Не добавлять Codex, AI или ботов в соавторы, `Co-authored-by`, подписи коммитов и автоматически создаваемые описания PR. Не использовать технический аккаунт ассистента для публикации.
- Если идентичность пользователя не настроена, уточнить её, а не придумывать. Это правило относится к Git-метаданным и не отменяет требования честно описывать использование AI, если это требуется заданием.
