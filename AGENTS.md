# СамоКеттик — правила разработки

## Область работы

- Следовать текущему заданию пользователя. Работать небольшими проверяемыми этапами; после этапа остановиться и дождаться отдельной команды. Не переходить к бизнес-логике в инфраструктурном этапе.
- Пользовательские глобальные правила сохранены в `docs/prompts/000-user-instructions.md`; они обязательны. Последующие явные инструкции пользователя имеют приоритет.
- Состояние согласования архитектуры и открытые вопросы — в `docs/DECISIONS.md`. Согласование основы не означает выбора почтового транспорта, зоны или финального UI.

## Код и данные

- React/TypeScript/Vite; Fastify/TypeScript; PostgreSQL/Drizzle. Строгая типизация, runtime-валидация границ, без `any` для обхода ошибок.
- Авторские стили только SCSS/Sass, по компонентам; `@use`/`@forward`. Не складывать всё в один stylesheet.
- Секреты только в локальных env; `.env` не коммитить, не выводить DATABASE_URL/пароли в журналы или ответы API.
- Бизнес-настройки — `config/demo.json`, технические — валидируемое окружение. Суммы — целые minor units, время — серверное; не доверять клиентскому времени/цене/статусу.
- Критические изменения состояния — PostgreSQL-транзакции и ограничения. Общий порядок блокировок: idempotency → user → vehicle → rental → interval → simulation → invoice/outbox. Почтовый worker блокирует только outbox. Не выполнять внешние вызовы внутри транзакции.
- Миграции генерируются Drizzle Kit, SQL проверяется и хранится в Git. Не применять `drizzle-kit push` к сохраняемому окружению. Не переписывать применённые миграции.
- Seed повторяемый, явно включается только в demo/test, не перезаписывает существующие данные. Демо-пользователи не означают готовую авторизацию.

## Дизайн

- Перед новым продуктовым UI исследовать опубликованные аналоги, записать ссылки/наблюдения. Перед существенной переработкой показать самостоятельные визуальные варианты и дождаться выбора.
- Не использовать декоративные номера, лозунги, случайные фигуры, ненужные бейджи и неизменённый внешний вид UI-библиотеки.
- Проверять RU/KY, в том числе реальные глифы Ңң Өө Үү, доступность, большой и маленький экран.
- Текущая страница проверки подключения — временный технический стенд, не утверждённый интерфейс аренды.

## Проверки и документация

- Вести `docs/WORKLOG.md`, `DECISIONS.md`, `PROMPTS.md`, `REQUIREMENTS.md`; сохранять существенные пользовательские задания точно.
- Использовать реальные ISO 8601 timestamps с часовым поясом. Отделять планы от выполненных команд и результатов. Не выдумывать успешные тесты и прошлое время.
- Для журналируемых команд: `node scripts/check.mjs npm run <script>` либо `node scripts/check.mjs docker ...`. Не передавать секреты аргументами.
- `npm run typecheck`, `npm test`, `npm run build`; изменения БД дополнительно `npm run test:db` на настоящем PostgreSQL, изолированно. Browser/API/БД flow проверять end-to-end.
- Не заменять доказательство конкурентности mock-БД или SQLite. Не скрывать сбои Docker, failed tests, audit findings и непроверенные внешние интеграции.
- Симуляция продвигается по elapsed DB time и сохранённым остаткам; pause/resume/finish сначала учитывают старый режим. Не переносить расчёт в браузер и не обнулять дробный расход на старте следующей поездки.
- NOTIFY/WS — сигналы сверки snapshots, не durable event log. При reconnect читать API. Локальное письмо — PostgreSQL mailbox + outbox ack в одной транзакции; не объявлять это внешней SMTP-доставкой.

## Git

- Перед первым commit проверить effective user.name/email и GIT_AUTHOR/GIT_COMMITTER overrides. Author и committer — пользователь, без Codex/AI/ботов/Co-authored-by.
- Не переписывать историю и не создавать фиктивные коммиты. После проверенного этапа предложить отдельный осмысленный commit; если пользователь просит только предложение, не делать commit автоматически.
- Не публиковать репозиторий и не делать push без задания на публикацию. Локальный Git уже является репозиторием проекта.
